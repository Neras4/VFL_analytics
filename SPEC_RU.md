# Техническая спецификация VFL Analytics Engine v0.1

**Дата спецификации:** 10 октября 2026. **Статус:** рабочее математическое ядро для исследовательских задач, не коммерческий/игровой генератор. **Уровень автономности:** чистые функции, без авторизации, коллектора, сети, MCP-сервера, БД и отправки составов.

## 1. Определение задачи

Нужно выбирать не сильнейших 11 игроков в вакууме, а **оптимальное решение для конкретной команды и горизонта**. Учитываем состояние состава, допустимые позиции, стиль, соперника, неопределённость о его решениях, календарь и стоимость будущих последствий.

Полный ожидаемый критерий будущего продукта:

\[
U(\pi)=\mathbb{E}_{\pi}\left[\sum_{t=1}^{T}\left(w_P P_t+w_D D_t-w_F F_t-w_C C_t\right)+\gamma V_T\right]-\lambda\,\mathrm{Risk}(\pi).
\]

**Важно:** это проектная целевая функция. `P_t` (очки за матч), `D_t` (развитие), `F_t` (потери формы/усталость), `C_t` (издержки), `V_T` (остаточная стоимость) сейчас не калиброваны в единой шкале; их **нельзя** складывать, пока не выбраны и не обоснованы веса. В v0.1 реализованы обособленные подзадачи и анализ чувствительности.

## 2. Входной контракт и источники

| Данные | Откуда в Assistant | Обязательность | Если отсутствует |

| `roster.players[].id,name,position,age,strength` | Normal | Для состава | Reject запись, issue |
| `fatigue`, `form` | Normal authoritative current-state | Для численной силы | Исключить из численной оптимизации, не ставить 0 |
| `realStrength` | Normal | Диагностика | Не домножать повторно |
| `specials` | Normal | Для будущих бонусов | Пока не моделировать |
| `playerDetails[].info.style,usefulness,contract` | Deep | По задаче | Unknown |
| `recentMatches` | Normal/Deep | Для вероятностей | Prior, не уверенный прогноз |
| `clubData.finances`, `deals` | Club Data | Для бюджета | Не рассчитывать финансовый ROI |
| `management.training/scouting/fitness` | Management | Для планирования | Не обещать оптимизацию сезона |
| `transferMarket.search`, `myBids` | Market | Для кандидатов | Не считать цену ставки ценой покупки |

Рекомендуемая схема data provenance: `source_url`, `collected_at`, `season`, `match_day`, `scope`, `missing_fields`, `collector_version`, `ruleset_version`, `model_version`. До матча фиксировать snapshot и прогноз, после матча хранить outcome отдельно — защита от look-ahead leakage.

**Граница:** `adapt_roster()` действительно читает подмножество полей `roster.players` v0.5.11 и пытается подтянуть отдельные поля `playerDetails[].info`. Контракт на реальной редактированной выгрузке *ещё не проверен*. Не все поля Assistant доступны из Normal (например, любимый стиль). Дополнительные поля не заполняются догадками.

## 3. Rules Engine — формулы

| Механика | Математика | Статус | Источник |
|---|---|---|---|
| Усталость | `S × (1 - fatigue/100)` | Компонент правила | §2.5 |
| Форма | `S × form/100` | Компонент; совмещение факторов как частичная модель | §2.6 |
| Совпадение любимого стиля | `+0.5%` за каждые изученные 20% до `+2.5%` | Реализовано | §2.10 |
| Коллизия любимого стиля игрока со стилем команды | `−1%`, при известных обоих стилях | Реализовано | §2.10–2.11 |
| Коллизии команд | Победитель по направленному циклу из шести | Реализовано; размер бонуса **не вводится** | §2.11 |
| Возрастной бонус капитана | По таблице 16–34 лет, с проверкой силы капитана | Реализовано **без Ка** | §2.8 |
| Взаимопонимание | `avg(line_modifiers)` на линии позиции; 12.5%, −5%, одинаковая национальность >=5% | Реализовано, только если указана геометрия | §2.12 |
| Выбор вида защиты | `attacking_positions>3 -> zonal`, иначе personal | Реализовано | §2.13 |
| Возрастное развитие молодёжи | Пороговая таблица возраста 16–23 | Реализовано | Раздел 3 «Рост силы молодых игроков» |
| Полезный ветеран | `played_minutes / team_official_minutes >=55%` | Реализовано как порог, не как бонус тренировки | Разделы 6–7 ветеранов |
| Бонусы позиций по стилям | Таблица/иллюстрация `pics/styles.png` | **Не реализовано** до извлечения точных коэффициентов | §2.10 |
| Не-своя позиция | Штраф зависит от соответствия позиции | **Не реализовано**, использован строгий фильтр | §2.4 и «Позиции игроков» |
| Спецвозможности | Ск, Г, Пд, Пк, Д, Км, Ка, Ат и др. | **Не реализовано**, надо отдельно проверять таблицы | Разделы спецвозможностей |
| Погода | Сближение сильных и слабых, зависит от номинальной силы | **Не реализовано** без численных коэффициентов | §2.16 |
| Домашний бонус/посещаемость | Зависит от заполнения стадиона | **Не реализовано** | §2.15 |
| Усталость/запас сил по ходу матча | Динамика действий и замен | **Не реализовано** | §2.7, страница усталости |
| Голы, удары, исход матча | Закрытые функции генератора | **Не реализовано** | Неизвестно |

### 3.1 Частичная реальная сила

При известных `form`, `fatigue`, `favorite_style` и документированном позиционном множителе:

\[
S^{partial}_{i,s,p}=R_i\frac{F_i}{100}\left(1-\frac{U_i}{100}\right)M_{i,s}Q_{s,p}.
\]

- `R` — номинальная сила;
- `F` — форма (например, `112`, не `1.12`);
- `U` — усталость в процентах;
- `M` — известный бонус/штраф взаимодействия любимого и выбранного стилей;
- `Q` — **только вручную подтверждённый** множитель позиции и стиля; по умолчанию `1` **с предупреждением о неполноте**, а не как утверждение VFL.

Отдельные капитанские и линейные бонусы добавляются в частичную оценку; порядок применения и влияние остальных спецвозможностей не объявляются эквивалентными генератору. `realStrength` из коллектора нужен как наблюдение для валидации, а не ещё один множитель.

### 3.2 Captain

Возраст `26,27: 1%`, `28:2%`, `29:3%`, `30:4%`, `31:5%`, `32:6%`, `33:7%`, `34:8%` силы капитана каждому **другому** игроку. `24–25:0`. `23..16` дают штраф от −1% до −8% **собственной** силы каждого другого игрока. Слабый капитан (ниже средней силы на поле) не даёт положительного бонуса без `Ка`. Для `Ка` нет выдуманного коэффициента — капитан исключается из автоматической оптимизации капитанов до формализации правила.

### 3.3 Chemistry

Для направленной линии A ← B: если одинаковые любимые стили, A получает `+12.5% × изученность стиля B`. При коллизии стилей и разных национальностях: −5%. Для игроков одной национальности модификатор не ниже +5%. В остальных известных случаях 0. Для разных национальностей и неизвестного любимого стиля: **null**, не ноль. Среднее по всем линиям игрока; если есть хотя бы один неопределённый компонент, точная средняя не заявляется.

## 4. Lineup Optimizer

**Вход:** `players[]`, `plans[]` (каждый — 11 уникальных слотов, 1 GK), список стилей. Если у игрока нет корректной формы/усталости, он не получает численного слота. Раненые/дисквалифицированные должны иметь `available=false`, если collector это достоверно определил. При `available=null` кандидат помечается `availability_unverified` и может участвовать **только в гипотетическом** подборе, не в гарантированно допустимом составе.

**Шаг A:** для каждого плана и стиля решить задачу назначения с матрицей `x_ij ∈ {0,1}`:

\[
\max \sum_{i\in Players}\sum_{j\in Slots} s_{ij}x_{ij},
\quad\sum_i x_{ij}=1,\quad \sum_j x_{ij}\le1,
\quad x_{ij}=0\text{ при недопустимой позиции.}
\]

Используем Hungarian algorithm (`scipy.optimize.linear_sum_assignment`) — **глобальный оптимум только для линейной подзадачи**.

**Шаг B:** перебрать ограниченное число альтернатив: исключить по одному ребру базового решения, пересчитать соответствующее matching, переоценить капитана и известные линии химии; выбрать лучшие. Это **эвристика** для нелинейной части, не оптимум всех перестановок. В будущем использовать mixed-integer or CP-SAT с нелинейной аппроксимацией.

**Выход:** топ вариантов, игрок/слот, `partial_strength`, partial captain/chemistry, список упущенных факторов и статус `partial_model`. Не выдавать «официальную силу» и «точную вероятность победы».

**Ограничение MVP:** не учитываются допуски `CM→DM`, `CD→SW` и др., если они не записаны в native `positions` или не подтверждены правилами; поэтому некоторые реально допустимые составы будут ошибочно помечены как невыполнимые — это сознательная **узкая область допустимых решений**, а не рекомендация.

## 5. Opponent Model (байесовская аналитика)

Модель не должна механически утверждать, что частота Спартака за сезон = вероятность Спартака против Ариэс.

Для каждого соперника выбираем завершённые матчи **до даты прогноза** и сохраняем: дата, стиль, соперник, home/away, относительная сила, формация, число атакующих, важность турнира (если есть).

Для стиля `s`:

\[
\alpha_s=\alpha_s^{prior}+\sum_m\boldsymbol1(Style_m=s)\,2^{-\Delta days_m/h}\,w(context_m,context_{next}).
\]

\[
P(s)=\frac{\alpha_s}{\sum_k \alpha_k}.
\]

MVP использует априорную равномерную массу 7 на 7 стилей и half-life 90 дней; контекстная близость (home/away, соотношение сил) задаётся **эвристическими** весами. Это *обобщённое байесовское приближение*, не оценка с гарантированной калибровкой. Показывать число матчей, эффективный вес выборки, 90% приблизительный интервал и флаг `limited_evidence`.

**Дальше:** раздельные модели для выбора стиля и расстановки; возможность смены менеджера (режим change point); обновляемый prior команды; календарный time split; сравнение с наивной частотой и равномерным baseline.

## 6. Match Decision Engine — оцениваем решение, не счёт

На начальном этапе движок честно отвечает на два независимых вопроса: (1) какой наш вариант сильнее по доступным точным компонентам; (2) какова вероятность коллизии по выбранному стилю.

\[
P_{win\,coll}(a)=\sum_{b:collision(a,b)=+1}P(b),\quad
P_{lose\,coll}(a)=\sum_{b:collision(a,b)=-1}P(b).
\]

Если пользователь **сам задаёт сценарную ценность** `C` в единицах `partial_strength`, можно посчитать условную полезность:

\[
U_C(a)=S^{partial}_a+C(P_{win\,coll}(a)-P_{lose\,coll}(a)).
\]

Monte Carlo с фиксированным seed по псевдоапостериорному распределению создаёт доверительный *внутримодельный* диапазон, а `risk_weight` даёт `mean − risk_weight × std`.

**Без численно обоснованного C движок обязан ответить `abstain_collision_magnitude_unknown`**, вернуть таблицу рисков и не делать математически фиктивный выбор стиля.

**Не implemented:** scoreline prediction, P(W/D/L), точный эффект «Спартак vs бей-беги», влияние супера/отдыха, условные замены/тактики, обоснованная модель паса/удара. Впервые разрешить P(W/D/L) только после калибровки на исторических матчах, сезонного out-of-sample и confidence checks.

## 7. Transfer Evaluator

Кандидат оценивается через пересчёт **всех одиннадцати позиций**:

\[
\Delta S_j = \max_{X\in\mathcal F(R\cup\{j\})} S^{partial}(X) - \max_{X\in\mathcal F(R)} S^{partial}(X).
\]

В данном прототипе оптимизатор нелинейной части приближённый, потому `ΔS` = относительная оценка, **не гарантированное усиление генератора**. У кандидата, который не выходит в оптимальном составе, прирост может быть нулевым, но глубина скамейки не оценена. Бюджет учитывается только как `cash >= price`; зарплата, торги, рыночный риск, возрастное развитие и контракт — отдельная следующая задача.

Следующий этап — три компонента полезности: `now` (вклад в состав), `future` (рост/старение/минуты), `risk+cost` (цена, зарплата, неполные скрытые параметры). Окончательное финансовое ROI нельзя считать из неподтверждённых коэффициентов.

## 8. Season Planner

Для возраста `16..23` пороги роста определены исходной таблицей. Для выбранной цели `g` и ожидаемого количества будущих официальных минут команды `M_future`:

\[
M^{required}_{player}=\max\left(0,\frac{threshold(age,g)}{100}\,(M_{played}+M_{future})-m_{player}\right).
\]

Пример: 16-летний игрок набрал 100 минут, команда сыграла 900 официальных минут и ожидает ещё 900. Для максимального +10 надо завершить сезон с 20% от 1800 = 360 минут; потребуется 260 минут дополнительно.

Для ветеранов аналогичный порог — 55%, но `useful` **не означает автоматически** тренировку спецвозможности: важны роль, уход на пенсию и другие требования.

**Далее:** оптимизация по расписанию игр и позиции каждого игрока, жёсткие лимиты общих минут, прогноз усталости и физической формы, планирование суперов/отдыхов, накопленных средств, контрактов и тренировок. Именно здесь будет уместен receding-horizon planner/MDP, но сначала нужны проверенные transitions.

## 9. Испытания, QA и критерии приемки

| Тест | Критерий |
|---|---|
| Unit rules | Точные таблицы, пороги, коллизии на границах |
| Contract Normal/Deep | Snapshot адаптер сохраняет известные поля и `null`; снапшоты v0.5.11 |
| Property based | Нет игрока в двух слотах; 1 GK; 10 полевых; ID уникальны |
| Missing data | Отсутствие формы/усталости не превращается в ноль или 100 |
| Outcome no leakage | Матчи target date/after исключены из обучения |
| Probabilistic correctness | Сумма стилевых вероятностей 1; intervals, positive priors |
| Calibration | Brier/log loss на хронологическом holdout против простых baseline |
| Rules regression | После новых правил сезон 80(?) запуск всей suite и compare score |
| Explainability | Каждый вклад и допущение имеют version/provenance |
| Security | Модуль вообще не видит cookies/пароли; MCP access read-only |

В текущем коде есть 12 проходящих тестов на synthetic fixtures. Это **не** означает acceptance по реальным матчам VFL. «Работает алгоритм» ≠ «проверена реальная игра».

## 10. Как расширять без переписывания ядра

```text
VFL Assistant 0.5.11
    ↓ [adapter validated against redacted exports]
Normalized snapshots + provenance
    ↓
Rules Engine (versioned) ─── Opponent Model (time-split, calibrated)
    ↓                              ↓
Lineup Optimizer ───── Match Decision Engine (risk/sensitivity)
    ↓                              ↓
Transfer Evaluator ────── Season Planner
    ↓
Structured JSON + uncertainty + evidence
    ↓
Future read-only authenticated MCP → Work
```

Не смешивать авторизацию сайта с математикой. Сбор HTML/JSON, доступ и токены — слой инфраструктуры, не слой оптимизации. Код ядра запускается локально без сети и независимо от хостинга.

## 11. Порядок следующих релизов

- **v0.2: Real snapshots acceptance** — redacted Normal/Deep, проверка адаптера, схемы позиционной совместимости, provenance.
- **v0.3: Rule-complete lineups** — матрица стилевых позиций, спецвозможности, капитан Ка, известные бонусы, точный legality filter; сопоставление с результатами VFL.
- **v0.4: Opponent validated** — матчи не только прошлых N, baseline, posterior calibration, анализ изменений поведения тренера.
- **v0.5: Decision calibrated** — оптимизация под матч, модели исхода и риска с честными intervals.
- **v0.6: Transfers + season** — горизонт, рынок, minutes quota, fatigue transitions, стоимость альтернатив.
- **MCP wrapper:** после контрактного теста, параллельно v0.2–v0.3, без изменений математических функций.

**Основной критерий качества:** предложение должно либо быть обосновано правилом/валидированной статистикой, либо сопровождаться явно указанным допущением и оценкой неопределённости. Если нет — система воздерживается от точной рекомендации.
